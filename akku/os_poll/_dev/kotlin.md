# os_poll research: kotlin

Scope: **synchronous** file-descriptor readiness with **bounded** waits — the
select/poll-style readiness query, not async. Kotlin has **no readiness API of
its own**: on the JVM it delegates to `java.nio.channels.Selector`; on
Kotlin/Native it exposes POSIX `poll`/`select` through cinterop. The coroutine
frameworks (Ktor CIO, `kotlinx.coroutines.select`) are layered on top and are
covered here only to delimit the synchronous subset. Unsourced claims are marked
`GUESS:` with the reason.

## 1. Standard library support

- **JVM (primary):** Kotlin/JVM uses the Java standard library directly —
  `java.nio.channels.Selector`, `SelectableChannel`, `SelectionKey`,
  `java.nio.channels.spi.SelectorProvider`. Kotlin defines **no** mirror of
  these; the types are the Java ones. Evidence: Ktor's JVM selector layer
  imports `java.nio.channels.*` and `java.nio.channels.spi.*` and declares its
  `Selectable` in terms of `java.nio.channels.SelectableChannel` and
  `SelectionKey` (`ktor-network/jvm/src/io/ktor/network/selector/JvmSelector.kt`).
- **Kotlin/Native:** readiness comes from the **`platform.posix`** cinterop
  library, which for Linux includes `poll.h`, `sys/poll.h` and `sys/select.h`,
  plus wrapper functions for the `FD_*` macros:
  `posix_FD_ZERO`, `posix_FD_SET`, `posix_FD_ISSET`. Source:
  `JetBrains/kotlin/kotlin-native/platformLibs/src/platform/linux/posix.def`
  (<https://raw.githubusercontent.com/JetBrains/kotlin/master/kotlin-native/platformLibs/src/platform/linux/posix.def>).
  The individual declarations (`poll`, `select`) are generated by cinterop from
  those headers; the `posix.def` proves the headers/functions are in scope.
- **Timeouts in the stdlib:** `kotlin.time.Duration` and the `kotlin.time`
  package provide duration values (`GUESS:` the exact Duration API surface was
  not fetched in this run; only its existence as the standard time type is
  assumed — reason: not needed for the readiness finding). Java's
  `java.util.concurrent.TimeUnit` is the JVM-side unit enum used by
  `WatchService.poll(long, TimeUnit)`.
- **Synchronous `Selector` is not exposed by Kotlin's own stdlib**: no
  `kotlin.*` readiness class exists. `GUESS:` reason — the Kotlin stdlib API
  index was not exhaustively searched; the positive evidence is that every
  readiness abstraction found delegates to `java.nio` or `platform.posix`.

## 3. Exposed APIs

### Ktor `SelectorManager` (the closest Kotlin-specific surface)
- `interface SelectorManager : CoroutineScope, Closeable`
  - `val provider: SelectorProvider` (the Java SPI provider)
  - `fun notifyClosed(selectable: Selectable)`
  - `suspend fun select(selectable: Selectable, interest: SelectInterest)`
- `enum class SelectInterest(val flag: Int)`: `READ(SelectionKey.OP_READ)`,
  `WRITE(SelectionKey.OP_WRITE)`, `ACCEPT(SelectionKey.OP_ACCEPT)`,
  `CONNECT(SelectionKey.OP_CONNECT)`, plus `AllInterests`, `flags`, `size`.
- Factory: `fun SelectorManager(dispatcher: CoroutineContext): SelectorManager`
  returns an `ActorSelectorManager`.
- JVM `Selectable` interface: `suspensions: InterestSuspensionsMap`,
  `isClosed: Boolean`, `interestedOps: Int`, `channel: SelectableChannel`,
  `interestOp(interest: SelectInterest, state: Boolean)`. On Native the same
  interface collapses to `descriptor: Int`.
- Sources: `ktor-network/jvm/src/io/ktor/network/selector/SelectorManager.kt`,
  `JvmSelector.kt`, `SelectableBase.kt`, klib API dump (all above).
- The readiness flags are exactly the Java constants — `SelectInterest.flag` is
  `SelectionKey.OP_*`, so the operation vocabulary is inherited from
  `java.nio.channels`. Source: `SelectorManager.kt` (above).

### `kotlinx.coroutines.selects.select`
- `inline suspend fun <R> select(crossinline builder: SelectBuilder<R>.() -> Unit): R`
- `SelectBuilder` clauses: `onJoin`, `onAwait`, `onSend`, `onReceive`,
  `onReceiveCatching`, `onTimeout(timeMillis: Long, block: suspend () -> R)`.
- `select` is **biased to the first clause**; `selectUnbiased` randomises.
  There is **no `default` clause** — callers use the non-suspending variant with
  `when`.
- Sources:
  <https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.selects/select.html>
  and
  <https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.selects/-select-builder/on-timeout.html>

### Java `Selector` API (inherited, see `java.md` §3)
- `selectNow()`, `select(long timeout)`, `select()`, `wakeup()`, `close()`,
  `keys()`, `selectedKeys()`; `SelectionKey.OP_*`, `readyOps()`,
  `interestOps()`. Sources: Java SE 21 javadoc (see `java.md` Sources).

## 4. Error representation

- JVM: exceptions flow through unchanged from `java.nio` —
  `IOException` (checked), `ClosedSelectorException`, `CancelledKeyException`,
  `ClosedChannelException`, `IllegalArgumentException`.
- Ktor wraps/uses these: `SelectorManagerSupport` catches `CancelledKeyException`
  while clearing interest ops, calls `cancelAllSuspensions(subject, cause)`,
  throws `ClosedChannelException()` and `ClosedSelectorException()`, and uses
  `IOException("Selectable is already closed")`; `error(...)` (IllegalStateException)
  for an invalid selectable state; a dedicated
  `ClosedSelectorCancellationException : CancellationException("Closed selector")`.
  Source: `ktor-network/jvm/src/io/ktor/network/selector/SelectorManagerSupport.kt`.
- `ClosedChannelCancellationException : CancellationException("Closed channel.")`
  is thrown for a closed selectable. Source:
  `ktor-network/jvm/.../SelectableBase.kt`.
- Kotlin has **no checked exceptions**; the compiler does not force catch of
  `IOException`. So on the JVM the "checked" property is lost at the Kotlin call
  site. `GUESS:` reason — this is a language property, not documented in the
  fetched pages; it is stated to warn that Kotlin callers do not get Java's
  compile-time catch pressure.
- `kotlinx.coroutines.select` surfaces failure as the clause's exception, and
  cancellation as `CancellationException` (with a "prompt cancellation
  guarantee"). Source: `select` API page (above).
- Native: a failing `poll`/`select` returns `-1` and sets `errno`; the cinterop
  `posix_errno()`/`set_posix_errno()` wrappers expose it. `GUESS:` the exact
  Kotlin signature (whether the binding throws or returns `-1`) — reason: the
  generated cinterop declarations were not fetched, only the `posix.def` header
  list and wrappers.

## 5. Ownership / lifetime semantics

- **The Java objects own the OS state**: the `Selector` owns the epoll/kqueue/
  poll fd, the `SelectableChannel` owns the socket, the `SelectionKey` is a
  registration token. Kotlin inherits exactly these rules (see `java.md` §5).
  Source: `java.md` (Java SE 21 javadoc).
- Ktor makes ownership explicit in Kotlin terms: `SelectorManager` is
  `Closeable`; `Selectable` extends `Closeable` **and** `DisposableHandle`.
  `SelectableBase.close()` is idempotent (`AtomicBoolean` CAS) and sets
  `_interestedOps = 0`; `ActorSelectorManager` registers
  `context[Job]?.invokeOnCompletion(onCancelling = true) { cause -> if (cause !=
  null) close() }`, i.e. the manager closes when its coroutine Job is cancelled.
  Sources: `SelectableBase.kt`, `ActorSelectorManager.kt`.
- The selector fd itself is owned by `ActorSelectorManager`, which opens it in a
  launched coroutine (`provider.openSelector()`) and closes it via
  `selector.use { ... }` when the processing loop ends. Source:
  `ActorSelectorManager.kt`.
- Ktor stores per-selectable state as the `SelectionKey` **attachment**:
  `channel.register(selector, ops, selectable)` and, in reverse,
  `key.attachment() as? Selectable`. This mirrors Java's attachment pattern.
  Source: `SelectorManagerSupport.kt`.
- On Native, ownership is manual: `Selectable.descriptor: Int` is a raw fd the
  caller must manage (no RAII wrapper in the interface). Source: klib API dump.

## 6. Blocking / non-blocking

- The underlying Java `Selector` is the blocking primitive (see `java.md` §6).
- Ktor drives it in a **single selection coroutine**: `ActorSelectorManager`
  launches one job that loops `processInterests` → `select(selector)` →
  `handleSelectedKeys`, using `selector.select(500L)` (a **hard-coded, bounded
  500 ms** block) before re-checking the queue, and `selector.selectNow()` when
  there are pending cancellations. Suspension/resumption of callers is handled
  via `suspendCancellableCoroutine`; cross-thread wakeups use an `AtomicLong
  wakeup` plus `selector.wakeup()` (`selectWakeup`). Source:
  `ActorSelectorManager.kt`; `SelectorManagerSupport.select`.
- Callers are **suspended**, not blocked: `SelectorManager.select` is a
  `suspend fun` that registers a continuation and returns when the interest is
  ready. The *synchronous subset* is therefore: one thread does bounded
  `Selector.select`, everything else is coroutine bookkeeping. Source:
  `SelectorManagerSupport.kt`.
- `kotlinx.coroutines.select` is the general coroutine multiplexer; it is not
  fd-based and is explicitly cancellable ("immediately resumes with
  `CancellationException`"). Source: `select` API page.
- Blocking vs non-blocking on Native is whatever `poll`/`select` is invoked with
  (0 ms timeout vs >0); no Kotlin abstraction forces it. `GUESS:` reason — no
  native selector implementation source was fetched in this run.

## 7. Kernel primitives and portability

- **JVM:** selected by `java.nio.channels.spi.SelectorProvider` — Linux
  `EPollSelectorImpl`, macOS/BSD `KQueueSelectorImpl`, generic Unix
  `PollSelectorImpl`, Windows `WindowsSelectorImpl` (see `java.md` §7 for the
  JDK source links). Kotlin reuses this provider directly: Ktor's
  `SelectorManagerSupport.provider = SelectorProvider.provider()`
  (`SelectorManagerSupport.kt`), and `NioEventLoopGroup`-style code passes a
  `SelectorProvider` explicitly.
- **Kotlin/Native:** portability is by platform library, not by runtime SPI.
  `platform.posix` gives Linux `poll.h`/`sys/poll.h` and `sys/select.h`; the
  macOS/iOS equivalents are separate `posix.def` files (same `platform.posix`
  package). Sources: Kotlin platform-libraries doc
  (<https://kotlinlang.org/docs/native-platform-libs.html>) and the Linux
  `posix.def` (above).
- Ktor provides native selector implementations under `ktor-network/nix`,
  `linux`, `macos`, `posix`; on Native the abstraction degrades to a raw
  `descriptor: Int`. Sources: `ktor-network` contents API; klib API dump.
- **No single Kotlin-level abstraction covers JVM + Native** in the stdlib; Ktor
  provides one via `expect`/`actual` (`SelectorManagerSupport` is jvm-only; the
  Native side uses different `actual`s). Source: klib API dump (separate
  `// Targets: [native]` section) and `JvmSelector.kt` (`expect interface
  Selectable`).

## 8. Timeouts

- Inherited JVM: Java's `Selector.select(long)` (timeout in **milliseconds**;
  `0` = indefinite; negative rejects; `selectNow()` = immediate). Source:
  `java.md` §8.
- Ktor's loop uses a **fixed 500 ms** bound and re-derives work from its queue
  each iteration; it does **not** compute a per-caller timeout, so cancellation
  latency is bounded by that 500 ms, not by a caller-supplied value. Source:
  `ActorSelectorManager.process/select`.
- `kotlinx.coroutines.selects.onTimeout(timeMillis: Long, block)` takes
  **milliseconds**; "if timeout is negative or zero, `block` is selected
  immediately"; the API is `@ExperimentalCoroutinesApi` and the `SelectBuilder`
  form is deprecated with error in favour of the extension function. Source:
  `onTimeout` API page (above).
- `Selectable` close cancels all pending suspensions with
  `ClosedChannelCancellationException`; manager close cancels with
  `ClosedSelectorCancellationException` — cancellation is exception-based, not a
  timeout result. Sources: `SelectableBase.kt`, `SelectorManagerSupport.kt`.

## 9. Bounded vs unbounded waits, EINTR and overflow

- **Bounded:** `Selector.select(long)` (ms), Ktor `select(selector, 500L)`,
  `WatchService.poll(long, TimeUnit)`, `onTimeout(timeMillis)`. **Unbounded:**
  `Selector.select()`, `WatchService.take()`. **Immediate:** `selectNow()`,
  `WatchService.poll()`. Sources: `java.md` §8–9; `ActorSelectorManager.kt`;
  `onTimeout` page.
- EINTR on the JVM is handled **inside the JDK** (`doSelect` retries while
  `IOStatus.INTERRUPTED` and subtracts elapsed time on a timed poll) — see
  `java.md` §9. Kotlin inherits this; Ktor never sees EINTR. Source: `java.md`;
  `ActorSelectorManager.kt` (no errno handling).
- Timeout overflow: `doSelect` clamps `Math.min(timeout, Integer.MAX_VALUE)`
  before the native call (see `java.md` §9). Kotlin code passing a `Long` ms
  timeout hits the same clamp. `onTimeout` accepts a `Long` but its underlying
  timer is the coroutine scheduler, not a kernel timeout. Sources: `java.md`;
  `onTimeout` page.
- On **Native**, EINTR is the caller's problem: `poll`/`select` return `-1` with
  `errno == EINTR`, and `posix_errno()` is available. `GUESS:` reason — no
  native selector loop source was fetched, so the retry policy of Ktor's native
  manager is not verified.

## 10. Interesting design decisions

- **Kotlin as a thin `expect`/`actual` skin over Java NIO.** The readiness
  vocabulary, errors and kernel selection are all Java's; Kotlin adds only
  coroutine suspension, an interest map and a single selection thread. This
  separation of "portable synchronous primitive" (Java) from "async scheduling"
  (Kotlin) is exactly the split `os_poll` should preserve. Sources:
  `JvmSelector.kt`, `SelectorManagerSupport.kt`, `SelectorManager.kt`.
- **Interest as an enum with a Java bit flag.** `SelectInterest(flag)` keeps the
  readable enum name while producing the exact `SelectionKey.OP_*` bit; `flags`
  and `size` precompute the arrays. Source: `SelectorManager.kt`.
- **Bounded polling loop with a queue, not per-caller timeouts.** A single
  500 ms `select` bounds wakeup latency and lets the loop drain a lock-free
  MPSC queue of interest changes. Source: `ActorSelectorManager.kt`.
- **Attachment as the state slot.** `key.attachment()` carries the `Selectable`,
  the same "one opaque object per registration" idea as Java. Source:
  `SelectorManagerSupport.kt`.
- **Cancellation as `CancellationException` subclasses**, so coroutine
  cancellation machinery and channel closure share one mechanism. Sources:
  `SelectableBase.kt`, `SelectorManagerSupport.kt`.
- **`select` is biased to the first clause** — a documented, deliberate
  determinism/priority decision (`selectUnbiased` for fairness). Source:
  `select` API page.
- **`onTimeout` with `<=0` meaning "immediately"** is a deliberate alternative
  to Java's `0` = "forever" — the same sentinel means the opposite in the two
  APIs, a strong argument for explicit timeout types. Source: `onTimeout` page.

## 11. Decisions NOT to copy

- **Hard-coded 500 ms select bound.** It fixes wakeup latency for every caller
  and is invisible in the public API. Mojo should take the bound from the caller.
  Source: `ActorSelectorManager.kt`.
- **Coroutine suspension as the only entry point.** Ktor's `select` is `suspend`;
  there is no synchronous, non-coroutine readiness query in the abstraction.
  `os_poll` is explicitly synchronous, so it must not require a coroutine
  runtime. Source: `SelectorManager.kt`.
- **Silent loss of Java's checked `IOException`** at the Kotlin boundary — the
  compiler stops enforcing handling. Mojo's `raises` should keep the error
  visible in the signature. (See §4; `java.md` §4; `mojov1/appendix/cheat-sheet`.)
- **Overlapping cancellation exception types**
  (`ClosedChannelCancellationException`, `ClosedSelectorCancellationException`,
  `ClosedChannelException`, `ClosedSelectorException`). Mojo can model these as
  a small typed error set. Sources: `SelectableBase.kt`,
  `SelectorManagerSupport.kt`.
- **`expect`/`actual` portability that hides a raw `Int` descriptor on Native.**
  The Native `Selectable.descriptor: Int` leaks an untyped fd; Mojo should own
  the fd in a typed handle. Sources: klib API dump; `JvmSelector.kt`.
- **`onTimeout`'s `<=0` = "now" sentinel**, opposite to Java's `0` = "forever".
  Do not replicate either sentinel. Source: `onTimeout` page.
- **Global `Job`-completion-driven close.** Tying selector lifetime to a
  coroutine context's cancellation is surprising for a synchronous library.
  Source: `ActorSelectorManager.kt`.

## 12. Ideas fitting Mojo

- **Keep the synchronous primitive separate from scheduling**, as Kotlin does
  (Java NIO underneath, coroutines on top): `os_poll` should ship only the
  synchronous bounded query; a coroutine/event loop stays a later library.
  Sources: `JvmSelector.kt`, `SelectorManagerSupport.kt`;
  `.repo/todo/os_poll.yml`.
- **Typed interest enum/`comptime` flags.** Kotlin's `SelectInterest(flag)`
  shows the value of a readable enum over raw ints; in Mojo make the flags
  `comptime` constants (or a `comptime` mask) with no runtime translation.
  (Mojo: `comptime NAME = value` — `mojov1/appendix/cheat-sheet`.)
- **`raises` for I/O errors.** Preserve Java/Kotlin's error visibility in the
  signature (`raises IoError`) instead of Kotlin's unchecked erasure. Sources:
  `java.md` §4; Mojo `raises` in `mojov1/appendix/cheat-sheet`.
- **Owned value results, no attachment object.** Instead of Java/Kotlin's
  single opaque `attachment`, return an owned readiness record (fd + flags).
  (Mojo ownership: `imm`/`mut`/`out` — `mojov1/keyword-conventions/imm`.)
- **Caller-supplied timeout, explicit type.** Replace the hard-coded 500 ms and
  both sentinel conventions with an explicit timeout argument (`mut`
  `Timeout`/`Duration`-like value) and distinct `try_now`/`block` constructors.
  (Sources: `ActorSelectorManager.kt`; `onTimeout` page.)
- **`__del__`-owned poller.** A `Poller` struct owning the epoll/kqueue/poll fd,
  closed in `__del__`, with `imm` borrowed query methods; the C-FFI layer is the
  portability boundary. (Mojo: `__del__`, `imm`/`mut` —
  `mojov1/keyword-conventions/imm`; `mojoNeeds: [pure-mojo, c-ffi]`.)
- **Compile-time platform selection** (`comptime if`) instead of
  `expect`/`actual` or a runtime `SelectorProvider`. (Mojo: `comptime if` —
  `mojov1/appendix/cheat-sheet`; Java contrast: `SelectorProvider` javadoc in
  `java.md`.)
